# Desktop Runtime SDK export

English | [中文](README.zh.md)

The `dsh.desktop-sdk/2` archive supplies the fixed DSH runtime, private Desktop Host, prepared Electron and interpreters, executable preparation tools, patch metadata and verification fixtures. It excludes Electron shell bundles, renderers, product artwork and `runtime/cli`. The upstream shell remains in this fork; an independent distribution owns its own shell source, compiler configuration, CLI, signing and installers.

Run these producer commands from the DSH repository root with its pinned dependencies installed on an Apple Silicon Mac. Build after committing source changes so the runtime artifact record and exported source identity name the same clean revision:

```sh
pnpm run build:official
pnpm --dir native/system run build:native
pnpm run release:pack --family dsh --out apps/desktop/.desktop-build/targets/mac-arm64/packed/dsh --concurrency 6
pnpm run release:pack --family vendor --out apps/desktop/.desktop-build/targets/mac-arm64/packed/vendor --concurrency 6
pnpm --dir apps/desktop-host pack --pack-destination "$PWD/apps/desktop/.desktop-build/targets/mac-arm64/packed/dsh"
pnpm --dir packages/sdk/desktop-runtime-contract pack --pack-destination "$PWD/apps/desktop/.desktop-build/targets/mac-arm64/packed/dsh"
pnpm --dir native/system/packages/entry pack --pack-destination "$PWD/apps/desktop/.desktop-build/targets/mac-arm64/packed/landlock"
npm pack ./native/system/packages/darwin-arm64 --pack-destination "$PWD/apps/desktop/.desktop-build/targets/mac-arm64/packed/landlock"
DSH_DESKTOP_UNSIGNED=1 DSH_DESKTOP_TARGET_PLATFORM=darwin DSH_DESKTOP_TARGET_ARCH=arm64 pnpm --dir apps/desktop run prepare:runtime
node apps/desktop/scripts/export-desktop-sdk.mjs --output /absolute/new-sdk-directory --target mac-arm64
```

For Linux x64 with glibc, use `linux-x64` in the target directories and export argument, `linux`/`x64` in the preparation environment, and `native/system/packages/linux-x64` for the native package. The locked primary runtime supplies Node, Python and pnpm; Electron uses `electron/electron`. Linux runtime preparation supplies no upstream shell CLI and does not enable release publication or automatic updates; distributors own their CLI. Export excludes optional native tooling for other platforms, architectures or libc implementations.

Windows x64 uses `win-x64` and the `win32`/`x64` preparation environment. Supply the published `node-addon-system` entry tarball in `packed/landlock`; this package has no Windows-specific native tarball. Windows operation support comes from the matching DSH dependency closure. Export requires a native Windows x64 producer. Prepared verification executes `electron/electron.exe`; packaged verification uses `--app <unpacked-directory> --executable <product.exe>` and its `resources` directory. The SDK excludes the upstream Windows CLI and does not sign or install the distributor's application.

Archive a completed export with `node apps/desktop/scripts/archive-desktop-sdk.mjs --sdk <sdk-directory> --output <new-archive.tgz>`. It preserves relative links without following dependency cycles, prints the SHA-256 and byte count, and refuses an existing output or an output inside the SDK (including directory aliases). Windows consumers must restore directory symlinks with their explicit directory type after validating the archive link graph; an untyped Node `fs.symlink` creates unusable file links to directories.

A complete Linux native build requires `musl-gcc`; the root official build prepares only the host addon. If the native source is unchanged, producers may instead supply canonical published native tarballs verified against registry integrity. Preserve their independent versions and original source receipts; do not attribute them to the DSH family build.

The output must not exist. Before writing output, export requires a clean source tree, an official client build from the current commit, and matching root, Desktop and client artifact versions. It also requires the matching native producer for `mac-arm64`, `linux-x64` or `win-x64`: the exporter copies installed native tooling dependencies, not a separately resolved target installation. These preflight failures leave no output; later failures retain a partial directory without a completed `dsh-desktop-sdk.json`. Archive the directory without dereferencing symbolic links and pin its digest in the distributor. The manifest records source identity, the artifact-verified runtime build record, Electron version and Host protocol version. Export refuses shell-owned output paths.

`shell-build/node_modules` contains the exact DSH packages required to compile a shell, including their declaration imports and the five upstream shell production dependencies. `shell-dependencies.json` records roots, archive-relative packed-package paths, versions and digests, independent of producer build storage. The distributor owns its pinned TypeScript, tsdown, Vite, React and Electron builder configuration; it must not infer that this SDK provides that compiler toolchain. The SDK retains its fixed Electron builder dependency closure for packaging consumers, and links the minimal app production dependencies inside the exported app directory.

The private workspace package [`@deepseek-ai/dsh-desktop-runtime-contract`](../../../../packages/sdk/desktop-runtime-contract/README.md) exports `./runtime-tree`, `./release`, `./host-protocol`, `./desktop-product`, `./core-package-set` and `./project-profile`. Export copies its packed JavaScript and declarations instead of compiling another implementation from shell sources. Shell adapters import these APIs instead of duplicating descriptor validation. The package also owns generic preparation helpers, packaged-runtime verification and the product-process acceptance runner; official build paths, signing and Host smoke orchestration remain in Desktop. `@deepseek-ai/dsh-desktop-host/protocol` supplies shared Host events, control requests, validators and the protocol version. Theme CSS and licensed fonts use `@deepseek-ai/dsh-client-ui-theme/styles/*`; primitives use the package root exports.

Run `node <sdk>/prepare.mjs --product <payload-root> --output <new-build-directory> --app-id <application-id> [--runtime-lock <qualified-pnpm-lock.yaml>]`. This composes only the runtime and a minimal application manifest. It executes no core compilation or source packing. The distribution then writes its own shell to `apps/desktop`, prepares `runtime/cli`, and seals the complete build inputs before packaging. Shell versions can be assigned after runtime preparation; runtime verification continues to use the SDK's fixed DSH version.

Preparation ignores the producer storage overrides `DSH_DESKTOP_BUILD_ROOT`, `DSH_DESKTOP_DOWNLOAD_CACHE` and `DSH_DESKTOP_PNPM_STORE_ROOT`. Its build and download paths stay inside the new output directory; its installation store is temporary.

An initial discovery run resolves third-party dependencies. A supplied runtime lock never falls back to resolution: core package and patch identities are checked before a frozen production install. Every run retains its validated lock at `<build-directory>/runtime-pnpm-lock.yaml` before installation; promote it only after preparation and verification succeed. The equivalent source-side variables are `DSH_DESKTOP_RUNTIME_LOCK` and `DSH_DESKTOP_RUNTIME_LOCK_OUTPUT`. Product resource links must resolve inside their tree without cycles and are materialized before integrity sealing.

`node <sdk>/verify.mjs --prepared <build-directory>` checks resources and runs real Host, native and Office smoke with isolated user data. On macOS, add `--app <application.app>` to inspect packaged resources and execute its declared binary. Linux packaged verification requires `--app <unpacked-directory> --executable <filename>` and reads `resources/dsh` and `resources/runtime`; verification requires the matching host. The SDK does not supply the product's builder configuration. This qualification does not cover graphical shell behavior, signing, notarization, update hosting or other platforms.

The manifest's `sdkApi.version` is `dsh.desktop-sdk-api/1`, independently of archive schema 2 and Host protocol 4. Its `profile`, `runtime`, `packagedRuntime` and `tools` fields identify `sdk/v1/profile.mjs`, `sdk/v1/runtime.mjs`, `sdk/v1/packaged-runtime.mjs` and `sdk/v1/tools.mjs`. These ESM entries export `createPluginProfile`, `verifyDesktopRuntime`, `verifyPackagedDesktopRuntime` and asynchronous `loadAsar`, respectively. Consumers validate the API version and exact paths before importing; unknown or incomplete declarations must fail rather than fall back to internal paths. `runtimeContract.profileModule` equals `sdkApi.profile`. Older schema-2 archives without `sdkApi` retain only their explicitly recognized legacy paths. Preparation internals remain private and cannot be removed while the SDK entrypoints depend on them.

Run exporter checks with `node --test apps/desktop/tests/export-desktop-sdk.test.mjs` and Host protocol checks with `pnpm exec vitest run apps/desktop-host/tests/protocol.spec.ts`. Exporter checks relocate the public APIs and product-process acceptance runner, including its package self-references through declared exports. The manifest’s `runtimeContract.profileModule` identifies the prepared-tree module that exports `createPluginProfile` for isolated CLI verification. The consumer must also compile its shell using only extracted SDK inputs and perform packaged-runtime checks.
