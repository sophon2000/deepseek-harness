# Agent Note: 独立发行所用的 Desktop 产物 SDK

Status: implemented

[English](2026-10-22-desktop-artifact-sdk.md) | 中文

## Problem

桌面打包在组合产品载荷时会编译整个 Harness checkout，并读取工作区清单、源码导入与补丁。独立维护的产品发行方无法在不保留源码 checkout 及其构建环境的情况下消费固定 Harness 版本。

## Decision

生产方导出按目标平台区分的 SDK，其中包含编译后的壳、运行时包归档、已准备的解释器、Electron 与可执行打包工具。工具保留相对资源布局，所复制包依赖全部在 SDK 内解析。导出器核验客户端产物记录，分别记录其运行时提交与工具 checkout 身份；未提交的工具输入保留摘要，不被标为干净状态。

发行方核验并固定 SDK 归档与产品载荷，在新目录中组合两者，发行构建必须提供已验证的生产依赖锁。发现阶段可以解析该锁，但已提供锁时绝不回退到重新解析。现有核心包归档、补丁、运行时完整性与 Host 冒烟检查保留在组合路径中。产品资源链接先按资源根目录校验，再物化后封存；运行时清单继续拒绝链接。冒烟 Profile 使用规范化后的临时主目录，避免 macOS 临时目录别名违反产品的规范存储路径要求。

## Alternatives considered

**复制完整源码 checkout。** 这仍让发行方依赖源码构建与工作区解析，没有建立固定产物消费方式。

**立即搬走整个 Electron 壳。** 壳、Host 生命周期与核心 API 仍共同演进。保留其源码维护方并导出可执行工具，可避免首次发行拆分时形成第二套实现。

**每次发行都重新解析 npm 范围。** 相同第一方输入可能选择不同的第三方依赖。单独验证的组合锁也固定了这部分输入。

## Consequences

产品发行方拥有品牌、安装器和发布策略，而无需编译 Harness。SDK 导出仍按目标平台区分，依赖生产方准备成功；它不是签名安装包。壳或 Host 变化仍要求新的 SDK 资格验证。首个受支持导出目标为 macOS arm64。签名、公证、图形流程验收及其他平台保留各自的验证要求。操作命令与失败保证见 [SDK 参考](../../../../apps/desktop/scripts/sdk/README.zh.md)。
