# Agent Note: Recoverable local subprocess operations

Status: proposed

English | [中文](2026-10-22-operation-cold-recovery.zh.md)

## Problem

A consumer reservation can outlive a crashed Host and runner. The existing subprocess service observes one live process range through `SubprocessHandle.waitForExit()`; it cannot reopen that range after restart. Windows ordinary subprocesses use an unnamed runner-owned Job per spawn. The suspended-create, assign, resume sequence also permits a runner crash to leave a suspended child outside the Job. No existing receipt, direct-process exit, missing PID, elapsed time, or ordinary task status proves the entire operation empty.

## Proposal

Add an explicit opt-in operation capability to the subprocess Service Definition, implemented by subprocess-local. Ordinary spawn and terminal behavior remain separate. A consumer creates one operation before any associated probe, encoder, Python process, or runner, persists its descriptor in the reservation, and launches every child through that operation. Zero active processes between sequential launches never completes an open operation. Providers without durable launch exclusion and native range observation return `unsupported`; legacy receipts without descriptors return `unverifiable` with reason `legacy-no-scope`.

The consumer owns business identity and reservation transitions; the provider owns native launch admission, durable seal, range termination, and fresh evidence. No new supervisor, consumer-provided PID list, or persisted result file establishes quiescence. The initial Windows implementation supports ordinary current-token subprocesses; terminals and restricted-token sandbox launches require their own verified integration before advertising support.

### Interface draft

The following outline summarizes the exported contracts in [operations.ts](../../../../packages/subprocess/subprocess/src/operations.ts). Opaque identifiers use repository brands; the source declarations own the complete signatures, including provider disposal. `OwnerKey` is generated by the trusted Host from its home, project, domain, and receipt identity. A client request carries only the receipt ID; the Host retrieves the descriptor and expected owner from its durable store.

```text
OperationDescriptor = {
  providerKind, providerVersion, locator: OpaqueLocator, ownerKey: OwnerKey
}
OperationScope = {
  descriptor: OperationDescriptor
  spawn(spec: SubprocessSpawnSpec): SubprocessHandle
  seal(signal?: AbortSignal): Promise<RecoveryResult>
}
OperationProvider = {
  create(ownerKey: OwnerKey): Promise<Created | Unsupported>
  recover(descriptor, expectedOwnerKey, signal?): Promise<RecoveryResult>
  verify(proof: QuiescenceProof, descriptor, expectedOwnerKey): boolean
}
RecoveryResult =
  { kind: sealed-quiescent, proof: QuiescenceProof }
  | { kind: active, sealed: boolean, reason: busy | aborted | draining }
  | { kind: unverifiable, reason: LegacyOrIntegrityOrNativeFailure }
  | { kind: unsupported, providerKind, providerVersion }
```

`create` returns only after provider identity and launch state are durable; no runner or target exists yet. The consumer persists the descriptor before calling `scope.spawn`. A failed reservation write must not be followed by a launch. Disposal or explicit recovery seals and terminates the operation; direct command completion does neither. Each child keeps its normal direct result and stream lifecycle, while only the operation reports operation quiescence.

Both `seal` and `recover` permanently reject future launches, terminate current members, and obtain fresh native evidence. An abort stops waiting; it never reopens admission or changes an unknown result into success. `active` covers a lock still held by a creator, a durable seal waiting for native drain, or an aborted observation. Failure to read identity, commit the seal, open/query the Job, or verify limits returns `unverifiable` with a structured reason. Unknown provider versions never fall back to PID inspection.

`QuiescenceProof` is a provider-issued in-process object with private issuer identity and bindings to descriptor, expected owner, machine identity, boot identity, and durable seal generation. `verify` accepts only evidence issued by that provider instance after current native observation; a JSON copy, forged object, proof for another operation, or evidence from a previous provider instance fails. Proof bytes are never accepted from clients or replayed from disk. Recovery after a provider restart obtains a new proof; a consumer persists its own reconciliation progress, not a substitute for native evidence.

### Windows admission and observation

Use one cryptographically random named Job for the operation and retain a Host handle across all sequential children. Enable `KILL_ON_JOB_CLOSE`, disable both breakaway limits, and ensure targets never inherit the Job or admission-lock handles. Each runner obtains only provider-authenticated operation instructions, validates identity, and uses `PROC_THREAD_ATTRIBUTE_JOB_LIST` with `STARTUPINFOEXW` at `CreateProcessW`. Recoverable launches must not use post-create `AssignProcessToJobObject`, including as a fallback. Failure to create directly inside the Job leaves the target unlaunched and fails closed.

Every creator and recovery attempt acquires the same OS-owned exclusive lock on an existing provider-owned admission file, opened without delete sharing. A creator holds that lock while validating immutable identity, checking the seal, acquiring the Job handle, creating the child atomically in the Job, and completing its initial resume or cleanup. A runner paused before lock acquisition rechecks after acquiring it. A runner killed while owning the lock releases it through kernel handle cleanup; any child already created is in the operation Job. A contender cannot create a replacement admission file when the existing one is missing.

Recovery acquires that lock, validates the trusted descriptor and expected owner, durably commits an irreversible seal, and only then observes the Job. Use a dedicated one-way seal record with exclusive creation and checked flush, never an in-place open-to-sealed overwrite that could be torn. Existing seal bytes require strict validation and a fresh successful durability check before retry can proceed. A torn, missing, inaccessible, or mismatched identity record withholds proof. Permanent seal retention prevents a delayed old runner from recreating an expired scope; any later garbage collection needs a separate safe retention design.

Recovery keeps the lock until the seal is durable, verifies Job limits, requests Job termination, and queries `JobObjectBasicAccountingInformation` until zero active processes. The retained named Job handle and permanent seal make the zero result stable against future provider launches. Every `OpenJobObjectW` failure, including exact object-not-found, withholds proof. Windows can remove a temporary object's name when its handle count reaches zero while pointer references still retain the object; termination can also wait for pending I/O. Namespace absence therefore cannot certify quiescence. Recovery must never create a replacement Job in order to query an empty object. The provider retains an authenticated Job handle across active and idempotent recovery attempts until disposal. Losing all Job handles after Host/runner death leaves the reservation unverifiable, even if a test independently waits for known processes to exit.

The descriptor stores provider installation identity, boot identity, owner key, operation nonce, Job name, namespace/session identity, and schema version in an authenticated provider-owned record. The locator is opaque and resolved beneath a configured trusted local root; it never supplies an arbitrary filesystem path. A copied record, alternate machine, boot mismatch, namespace mismatch, or unknown version withholds proof. The implementation reads the kernel boot identifier with `NtQuerySystemInformation` class 90 and rejects an unsupported status, result length, or zero identifier. This native ABI dependency still needs platform qualification; PID absence, process age, an estimated boot time, and a new provider run ID cannot substitute. Boot changes remain `unverifiable` until a separately validated policy is implemented.

The trusted store must reject reparse-point substitution and have an explicit Windows DACL. The threat model excludes arbitrary code already executing with the trusted Host's full filesystem and handle privileges; a Job is not a security sandbox against such code. The supported process range includes normal `CreateProcess` descendants and detached children with breakaway disabled. Out-of-process brokers such as WMI process creation are outside Job inheritance; a consumer using those brokers cannot claim the same operation guarantee without an additional verified provider.

The local provider's documented fallback and per-spawn Job lifetime remain valid for existing callers. This proposal does not upgrade their evidence or recover historical anonymous Jobs. The active-note supersession check found no existing note owning operation cold recovery; existing per-spawn containment decisions remain applicable.

### Host coordination

The proposed Host port can retain `sealed-quiescent | active | unverifiable | unsupported`. Add `expectedOwnerKey` to recovery and require provider verification of its in-process proof before releasing a reservation. Resolve and authenticate the provider record, then compare its owner to the independently derived expected owner before opening or terminating its Job; exchanging two valid locators between receipts must fail. Owner derivation includes a trusted durable home nonce; an existing home marker without that identity requires a separately versioned Host migration, never an inferred binding for legacy receipts. A Host marks durable `reconciling`, performs idempotent domain cleanup and terminalization, and releases the journal reservation last. Retrying after a Host crash reopens the same descriptor and obtains fresh provider evidence. DSH does not own media cleanup, task terminalization, capacity accounting, or the consumer's dependency pin.

Normal success and cancellation also require a permanent operation seal and verified operation quiescence before releasing capacity. The Host lock order is project lifecycle writer followed by capacity; cleanup must not acquire a project writer while holding capacity in the opposite order. DSH owns only its admission lock and never calls domain cleanup or acquires consumer locks while holding it. The consumer adapter needs a real concurrent barrier test in addition to fake-provider coordination tests.

### Microsoft references

The job-list creation attribute is available on Windows 10 and Windows Server 2016 onward; its native value storage must outlive the attribute list. See [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

Job descendants, breakaway flags, nested accounting, and Job destruction semantics are documented in [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Named-object lookup uses [OpenJobObjectW](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-openjobobjectw); job-wide termination uses [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject). Checked durable seal writes use [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

[Life Cycle of an Object](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/life-cycle-of-an-object) distinguishes namespace lifetime from pointer references. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) documents asynchronous termination and pending I/O. These rules require missing named Jobs to remain unverifiable; no native residual-process reproduction is claimed.

## Alternatives considered

**Persist PID and runner status.** Rejected because PID reuse, unknown grandchildren, and a crashed runner cannot establish the operation's native range or prevent a delayed launch.

**Name the existing per-spawn Job and query zero.** Rejected because a later runner can create work after the observation and because one operation can contain several sequential children.

**Keep suspended creation followed by assignment.** Rejected for recoverable launches because killing the runner between those calls can leave an uncontained suspended child.

**Add a supervising daemon.** Rejected because this capability must recover through durable provider state and kernel ownership without a new long-lived process. A daemon would also need its own crash-recovery proof.

**Trust a stored completion result.** Rejected because a file can be stale or client-supplied and cannot establish current native quiescence or launch exclusion.

## Acceptance criteria

Real Windows tests must cover reservation-before-runner, a late runner blocked by a durable seal, forced runner death immediately after atomic creation before resume, direct child exit with a live grandchild, detached descendants, denied breakaway, simultaneous Host/runner death, native query failure, identity mismatch, and sequential children separated by a zero-member interval. Negative tests must retain the reservation after PID reuse or absent PID, legacy records, unsupported providers, forged proof, descriptor substitution, torn identity or seal, write or flush failure, and repeated recovery.

Recovery interrupted by process death must be retried at each durable-write and native-query checkpoint. Actual OS reboot during recovery requires an explicitly coordinated manual Windows run; the test harness must not restart the user's machine. A simulated boot mismatch is a separate negative test and does not replace reboot validation. Platform failures remain failures; no weakened assertion or fallback can earn the capability flag.

The opt-in provider and Node/Koffi Job-list path are implemented on the isolated branch. Native tests cover durable admission, multiple launches, descendant containment, issuer verification, write and query failures, actual Host/runner crashes, and recovery-process death before and after seal creation, write, flush, Job open, limits query, termination, and accounting query. Retry revalidates complete seals and obtains fresh native evidence while the same authenticated Job remains reopenable; an empty interrupted seal permanently withholds proof. Disposal closes recovery admission before draining owned Jobs, and rejects calls made while closing or after disposal. A Cordis Loader composition test exercises the public factory. The [artifact smoke](../../../../packages/subprocess/subprocess-local/verify/operation-artifact.mjs) exercises ordinary package exports and built runners in concurrent independent consumers. These checks do not qualify a shipping artifact: actual OS reboot, power-loss durability, consumer integration, and repository build and packed-install checks remain separate acceptance requirements. `active.sealed = false` leaves seal state unconfirmed; it never authorizes reopening admission.

## Risks

Power-loss durability, object namespace identity, reparse points, DACLs, and boot identity need explicit native validation. A crashed holder can release an OS lock while queued work still exists, so every runner must validate under the lock immediately before native creation. Breakaway denial can prevent programs that require another Job from launching; silently weakening containment would invalidate recovery. Retaining permanent seals consumes disk space. Blocking file locks must use bounded asynchronous admission so a busy creator cannot freeze the Host event loop. Existing legacy reservations remain unverifiable and require a separate operator policy.
